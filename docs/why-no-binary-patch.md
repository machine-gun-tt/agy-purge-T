# 为什么这次不改二进制

dsh-purge 的做法是备份 `@deepseek-ai/*` 里的文件、按模式替换、再写 shim。那是对的选择——**因为 DeepSeek Harness 没有对外的扩展点**。提示词组装、审批闸门、沙箱策略全在包内，除了改包没有别的入口。

Antigravity 不是这种情况。它把 `hooks.json` 做成了一等公民，而且位置恰好在上游：

```
用户输入
   │
   ├─ PreInvocation ───────── 模型调用之前  ← 注入覆盖稿
   │
   ├─ 模型调用
   │
   ├─ PreToolUse ──────────── 审批闸门本身  ← 直接 allow
   │
   ├─ 工具执行
   │
   └─ Stop ───────────────── 收工决策点    ← 强制续跑
```

`PreToolUse` 不是"模拟点击允许"，而是**闸门的决策入口**；`PreInvocation` 不是"往文件里塞字符串"，而是**调用链上的一次合法注入**。这两点已经在链路的最上游，改宿主字节带不来任何额外能力，只带来成本：

| | 改 `app.asar` / `.exe` | 用 hooks |
| --- | --- | --- |
| 效果 | 与 hooks 相同（甚至更弱：管不到 `PreInvocation` 注入） | 完整 |
| Antigravity 升级 | 每次升级都可能碎，字符串匹配失败就是静默失效 | 不受影响 |
| 完整性/签名 | 可能触发校验，属于"把软件改坏"的路径 | 不触碰 |
| 失败模式 | 应用起不来 | 钩子返回 `{}`，退回宿主默认 |
| 回滚 | 依赖备份字节 | 删一个目录 + 删一个键 |

所以 `agy-purge` 的取舍是：**把复杂度花在正确的位置**——钩子的超时、坏输入、版本差异（见 [hooks-protocol.md](hooks-protocol.md)），而不是花在 asar 重打包上。

## 那"破甲"还在不在

在。破甲的本质是「让宿主层的默认策略不再压过操作者的意图」，而不是「必须改一个二进制文件才算数」。四条路径都成立：

1. 覆盖稿每轮进 `systemMessage` → 指令位阶被改写；
2. 审批闸门返回 `allow` → 不再有"是否允许"这一步；
3. `Stop` 拉回循环 → 不再有"模型自己收工"；
4. 审计日志 → 你随时能看到它到底做了什么。

## 什么时候还是得改二进制

只有一种情况：宿主把某个行为**硬编码进了没有钩子的路径**，而且没有设置项。真遇到这种，正确做法也不是改 `app.asar`，而是：

1. 先在 `~/.gemini/config/config.json` 的 `userSettings` 里找对应开关；
2. 再查 `language_server.exe --help` 有没有对应 flag；
3. 都没有，才考虑 `--user-data-dir` 之类的外部覆盖，最后才是改包——而且必须留 `*.bak` 与一键回滚。

`agy-purge` 目前没有任何一项需要走到第 3 步。如果未来某个版本需要，它会以**可选、默认关闭、单独可回滚**的形式出现，而不是默认路径。
